# Лабораторная работа №3. Безопасность, роли, логирование, CI

Расширение ЛР2 (SPA на React + REST API на Node.js + PostgreSQL + Docker). Предметная область прежняя —
«Список задач» с файлами, но теперь приложение закрыто авторизацией.

## Что требовалось и где это реализовано

| № | Требование | Реализация | Где смотреть |
|---|---|---|---|
| 1 | **Модель доступа, ≥ 3 роли, на временных ключах** | Роли `viewer` / `user` / `admin`. Ключи: **access-токен** (JWT, 15 мин, в памяти браузера) + **refresh-токен** (случайный, 7 дней, httpOnly-cookie, в БД только его хеш, ротация при каждом обновлении, обнаружение повторного использования) | `server/src/security/tokens.js`, `middleware/auth.js`, `services/sessions.js`, `routes/auth.js` |
| 2 | **Ошибки и коды по стандартам HTTP** | 200/201/202/204; 400, 401 (+`WWW-Authenticate`), 403, 404, 405 (+`Allow`), 409, 413, 415, 429 (+`Retry-After`), 500. Единый JSON-формат ошибки с `code` и `requestId` | `server/src/errors.js`, `http.js`, `app.js` |
| 3 | **Защита от подбора, контроль активных подключений, восстановление через e-mail** | Блокировка аккаунта после N неудач (429), лимит частоты запросов по IP, список/завершение подключений, лимит числа сессий, письмо со ссылкой на одноразовый токен | `services/loginAttempts.js`, `security/rateLimit.js`, `services/sessions.js`, `mailer.js` |
| 4 | **Структурированное логирование** | `pino`: одна строка JSON на событие; id запроса, пользователь, событие (`auth.login.failed`, `auth.lockout`, ...); секреты маскируются | `server/src/logger.js` |
| 5 | **Автоматическая проверка кода** | GitHub Actions: ESLint (сервер и клиент) → тесты API на PostgreSQL → сборка клиента → сборка Docker-образов | `../.github/workflows/lab3-ci.yml` |

### Роли

| Действие | viewer (наблюдатель) | user (пользователь) | admin |
|---|:-:|:-:|:-:|
| Смотреть задачи и скачивать файлы | ✅ | ✅ | ✅ |
| Создавать задачи | ❌ 403 | ✅ | ✅ |
| Менять/удалять задачи и файлы | ❌ 403 | только **свои**, чужие — 403 | ✅ все |
| Управление пользователями (роли, блокировки, подключения) | ❌ | ❌ | ✅ |

Публичная регистрация создаёт роль `user`. Роль меняет только администратор; роль всегда читается из БД,
поэтому изменение действует **немедленно**, без повторного входа.

cd "D:\Study\Term 7\SPP\lab3"

| `admin@example.com` | `Admin12345!` | admin |

Остановка: `Ctrl+C`; с удалением данных: `docker compose down -v`. Если изменили код — `docker compose up --build`.
Настройки (порты, секреты, лимиты) — переменные окружения / файл `.env` (образец: `.env.example`).
**Перед реальным использованием смените `JWT_SECRET` и отключите `SEED_DEMO_USERS`.**

## Как проверить лабораторную

### 1. Роли и ключи (в браузере)
1. Войдите как `viewer@example.com`: кнопки «Новая задача» нет, действия над карточками скрыты, вверху плашка о режиме просмотра.
2. Выйдите, войдите как `user@example.com`: создайте задачу, прикрепите файл. Это **ваша** задача — можно менять и удалять.
3. Войдите как `admin@example.com`: видны все задачи и вкладка «Пользователи». Админ может править чужие задачи.
4. Зайдите `user` → вкладка «Пользователи» отсутствует; запрос `GET /api/users` вернёт **403**.
5. Админ в «Пользователи» меняет роль `user` на `viewer`; у того пользователя после обновления страницы пропадают кнопки (права действуют сразу).
6. **Временность ключей:** access-токен живёт 15 минут. Чтобы увидеть обновление за секунды, запустите с
   `ACCESS_TOKEN_TTL_SECONDS=20` (в `.env`), поработайте > 20 с — в DevTools → Network видно, что после
   `401 TOKEN_EXPIRED` клиент сам вызывает `POST /api/auth/refresh` и повторяет запрос; пользователь ничего не замечает.

### 2. Защита от подбора
1. На экране входа введите неверный пароль для `user@example.com` — сообщение «Осталось попыток: N».
2. После 5-й неудачи — **429** и блокировка на 15 минут; даже правильный пароль не пустит.
3. Админ → «Пользователи» → у аккаунта значок «Вход заблокирован» → «Разблокировать».
4. Лимит запросов по IP (для проверки из консоли PowerShell):
   ```powershell
   1..40 | % { curl.exe -s -o NUL -w "%{http_code} " -X POST http://localhost:8080/api/auth/login -H "Content-Type: application/json" -d "{\"email\":\"x$_@t.io\",\"password\":\"abc\"}" }
   ```
   Первые ответы — `401`, затем `429` (и заголовок `Retry-After`).

### 3. Контроль активных подключений
1. Войдите под одним аккаунтом в двух браузерах (или обычное окно + инкогнито).
2. Вкладка «Безопасность»: видны оба подключения (браузер/ОС, IP, активность), текущее помечено.
3. Нажмите «Завершить» у второго — во втором браузере при следующем действии появится «Сессия завершена. Войдите снова.»
4. «Выйти на всех остальных устройствах» — завершает всё, кроме текущего. Админ видит и закрывает подключения любого пользователя.
5. Лимит подключений: 6-й вход вытесняет самое старое (`MAX_SESSIONS=5`).

### 4. Восстановление доступа по e-mail
1. Экран входа → «Забыли пароль?» → email `user@example.com` → сообщение (одинаковое для любого адреса — нет утечки, зарегистрирован ли email).
2. Откройте **http://localhost:8025** — там письмо со ссылкой, нажмите её.
3. Задайте новый пароль → войдите. Старые сессии завершены, блокировка (если была) снята.
4. Ссылка **одноразовая** и живёт 30 минут: повторное открытие — «Ссылка недействительна…».

### 5. Коды ответов HTTP (консоль)
```powershell
curl.exe -i http://localhost:8080/api/tasks                      # 401 + WWW-Authenticate
curl.exe -i -X DELETE http://localhost:8080/api/auth/login       # 405 + Allow: POST, OPTIONS
curl.exe -i http://localhost:8080/api/nope                       # 404 (JSON)
curl.exe -i -X POST http://localhost:8080/api/auth/register -H "Content-Type: application/json" -d "{}"   # 400 + details
```
Токен для запросов с авторизацией можно взять из ответа `POST /api/auth/login` (поле `accessToken`) и передать так:
`-H "Authorization: Bearer <токен>"`.

### 6. Логи
```powershell
docker compose logs -f server
```
Каждая строка — JSON: `{"level":"warn","time":"...","req":{"id":"...","method":"POST","url":"/api/auth/login"},"event":"auth.login.failed","email":"...","failures":2,...}`.
События: `auth.login.success|failed`, `auth.lockout`, `auth.refresh.reuse_detected`, `session.revoked`, `auth.reset.requested|completed`,
`access.denied`, `rate_limit.exceeded`, `user.role_changed` и др. Пароли, токены и cookie в логи не попадают (маскируются).
Тот же `requestId` возвращается клиенту в теле ошибки и заголовке `X-Request-Id` — по нему легко найти запись в логе.

### 7. Автоматические проверки (локально то же, что делает CI)
```powershell
cd lab3\server ; npm ci ; npm run lint ; npm test     # тесты требуют PostgreSQL (см. ниже)
cd ..\client   ; npm ci ; npm run lint ; npm run build
```
Для тестов нужна БД: `docker run -d --name spp-pg -e POSTGRES_USER=spp -e POSTGRES_PASSWORD=spp -e POSTGRES_DB=spp -p 5432:5432 postgres:16-alpine`.
В репозитории CI запускается автоматически при push/pull request (вкладка **Actions**). Workflow лежит в
`.github/workflows/lab3-ci.yml` в **корне** репозитория (GitHub ищет workflow только там).
Тесты (18 сценариев) покрывают роли и 403, истёкший/поддельный токен, ротацию refresh, блокировку, лимит подключений,
восстановление пароля, коды 400/401/403/404/405/409/413/415/429.

## API (сводка)

| Метод и путь | Доступ | Успех | Основные ошибки |
|---|---|---|---|
| `POST /api/auth/register` | все | 201 | 400, 409, 429 |
| `POST /api/auth/login` | все | 200 | 400, 401, 429 (блокировка) |
| `POST /api/auth/refresh` | cookie | 200 | 401 |
| `POST /api/auth/logout` | cookie | 204 | — |
| `GET /api/auth/me` | любая роль | 200 | 401 |
| `POST /api/auth/change-password` | любая роль | 204 | 400, 401 |
| `GET/DELETE /api/auth/sessions`, `DELETE /api/auth/sessions/:id` | любая роль | 200/204 | 401, 404 |
| `POST /api/auth/forgot-password` | все | 202 | 400, 429 |
| `POST /api/auth/reset-password` | токен из письма | 204 | 400 |
| `GET /api/tasks`, `GET /api/tasks/:id`, `GET .../attachments/:aid` | viewer+ | 200 | 401, 404 |
| `POST /api/tasks` | user+ | 201 | 400, 403 |
| `PUT/PATCH/DELETE /api/tasks/:id`, `POST/DELETE .../attachments` | автор или admin | 200/201/204 | 400, 403, 404, 413, 415 |
| `GET /api/users`, `PATCH/DELETE /api/users/:id`, `POST /api/users/:id/unlock`, `GET/DELETE /api/users/:id/sessions` | admin | 200/204 | 403, 404, 409 |
| `GET /api/health` | все | 200 | — |

Формат ошибки: `{"error":{"code":"FORBIDDEN","message":"...","details":[{"field":"..","message":".."}],"requestId":"..."}}`.

## Принятые решения (коротко)
- **Access-токен в памяти, refresh в httpOnly-cookie** (`SameSite=Strict`, путь `/api/auth`): JS не может прочитать refresh-токен (защита от XSS), а cookie не уходит на чужие сайты (защита от CSRF).
- **Токен проверяется ещё и по БД:** завершение сессии/смена роли/удаление пользователя действуют мгновенно, несмотря на «подписанный» JWT.
- **Ротация refresh-токена:** при каждом обновлении выдаётся новый; повторное предъявление старого (признак кражи) отзывает всю сессию.
- **Пароли:** `scrypt` + соль (встроено в Node.js). **Нет утечки существования аккаунта:** одинаковые ответы и время при неверном пароле/неизвестном email, `forgot-password` всегда 202.
- **Скачивание файлов** идёт через `fetch` с токеном (ссылке `<a href>` нельзя передать заголовок `Authorization`).
- **Ограничения учебной версии:** счётчик частоты запросов хранится в памяти процесса (для нескольких экземпляров сервера нужен Redis); нет подтверждения email при регистрации.
