## 1. Что реализовано по условию

| Требование задания | Где реализовано |
|---|---|
| Список задач | `GET /tasks` → `views/index.ejs` |
| Статус выполнения задачи | поле `status`: `todo` / `in_progress` / `done` |
| Фильтрация по статусу | `GET /tasks?status=...`, ссылки-вкладки вверху списка |
| Ожидаемая дата завершения | поле `dueDate`, подсветка просроченных задач |
| Прикрепление файлов к задаче | `multer`, поле `attachments`, можно добавлять как при создании, так и потом на странице задачи |
| Рендеринг на сервере | все страницы — результат `res.render(...)` на EJS, клиент получает готовый HTML |
| Отправка данных через формы | все мутации (создание, смена статуса, добавление/удаление файла, удаление задачи) — обычные HTML `<form>` с `GET`/`POST`, без `fetch`/`XHR`/AJAX |

## 4. Основные маршруты (routes)

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/tasks` | список задач, опционально `?status=todo\|in_progress\|done\|all` |
| GET | `/tasks/new` | форма создания задачи |
| POST | `/tasks` | создать задачу (`multipart/form-data`, файлы + поля) |
| GET | `/tasks/:id` | страница одной задачи |
| POST | `/tasks/:id/status` | сменить статус (форма с `<select>`) |
| POST | `/tasks/:id/attachments` | добавить файлы к существующей задаче |
| POST | `/tasks/:id/attachments/:attachmentId/delete` | удалить один файл |
| GET | `/files/:filename` | скачать файл с исходным именем |
| POST | `/tasks/:id/delete` | удалить задачу целиком (и её файлы) |

## 5. Немного теории: что такое SSR

**SSR (Server-Side Rendering)** — подход, при котором **HTML-разметка
страницы формируется на сервере** для каждого запроса и отдаётся браузеру уже
готовой к отображению. Это противоположность **CSR (Client-Side Rendering)**,
где сервер отдаёт почти пустой `index.html` + JS-бандл, а всё содержимое
страницы строит JavaScript в браузере уже после загрузки (типичный подход
React/Vue/Angular SPA).

### Как это выглядит в данном проекте

1. Браузер делает обычный HTTP-запрос, например `GET /tasks?status=done`.
2. Express-роут получает запрос, достаёт данные (`store.getAll(...)`).
3. Данные передаются в **шаблон EJS** (`res.render('index', { tasks, ... })`).
4. EJS **на сервере** подставляет данные в HTML-шаблон и получает строку
   готовой HTML-страницы.
5. Эта строка целиком отправляется клиенту как обычный HTML-ответ.
6. Браузер просто отображает полученный HTML — никакого JS для построения
   интерфейса не требуется и не используется.

Каждое действие пользователя (создать задачу, сменить статус, прикрепить
файл, отфильтровать список) — это **новый HTTP-запрос** (переход по ссылке
или отправка формы), на который сервер **заново** рендерит всю страницу
целиком. Состояние приложения нигде не хранится в JS в браузере — оно живёт
на сервере (в `data/tasks.json`) и каждый раз "стекает" в HTML.

### Почему тут используются именно HTML-формы, а не fetch/AJAX

Обычная HTML-форма (`<form method="POST">`) — это встроенный в браузер
механизм, который:

- сериализует свои поля,
- отправляет их как тело HTTP-запроса (или query-string для `GET`),
- **сам** переходит на страницу, которую вернул сервер в ответе.

Никакого JavaScript для этого не нужно — это работает даже с полностью
отключённым JS в браузере. Именно поэтому такой подход — самый "чистый"
пример SSR: сервер не просто рендерит первую загрузку, а вообще является
единственным местом, где строится разметка и куда отправляются данные.

Для файлов форма использует `enctype="multipart/form-data"` — это единственный
способ передать бинарные файлы через обычную HTML-форму. На сервере такие
запросы разбирает `multer` (парсер `multipart/form-data` для Express),
сохраняя файлы в `uploads/` и добавляя в `req.files` информацию о каждом
файле (сгенерированное имя на диске, оригинальное имя, размер и т.д.).

### SSR vs CSR — сравнение

| | SSR (этот проект) | CSR / SPA |
|---|---|---|
| Кто строит HTML | сервер, на каждый запрос | браузер, через JS после загрузки |
| Первая отрисовка | быстрая — пришёл готовый HTML | обычно медленнее — нужно скачать и выполнить JS-бандл, потом запросить данные |
| SEO | простой — поисковики видят готовый HTML | сложнее — нужен prerendering/SSR-фреймворк (Next.js и т.п.) |
| Работа без JS | работает | не работает |
| Переходы между страницами | полная перезагрузка страницы | обычно без перезагрузки (быстрее, но требует роутинга на клиенте) |
| Нагрузка на сервер | выше (рендер на каждый запрос) | ниже (сервер часто отдаёт только JSON API) |
| Типичный стек | Express+EJS/Pug/Handlebars, Django, Rails, PHP | React/Vue/Angular + REST/GraphQL API |

### Где твой опыт фронтендера тут пригодится/не пригодится

- **State на клиенте не нужен** — нет Redux/Zustand/React state, потому что
  состояние живёт на сервере, а не в браузере.
- **Роутинг — это буквально серверные роуты Express** (`app.get`, `app.post`),
  а не `react-router`.
  а "переход между страницами" — это обычная навигация браузера.
- **Шаблонизатор (EJS)** — концептуально похож на JSX, но выполняется на
  сервере и один раз на запрос, а не реактивно перерисовывается при
  изменении состояния.
- Как в Node.js-бэкенде, который ты уже писал: Express-мидлвары
  (`express.urlencoded`, `multer`, `methodOverride`) работают точно так же,
  просто вместо `res.json(...)` в конце пишем `res.render(...)`.

### Гибридные подходы (для общего кругозора)

Современные фреймворки (Next.js, Nuxt, Remix, SvelteKit) часто совмещают
SSR и CSR: первая загрузка страницы рендерится на сервере (быстро, хорошо
для SEO), а после этого приложение "оживает" на клиенте (гидратация,
*hydration*) и дальше ведёт себя как SPA. Наш пример — **классический,
"чистый" SSR без гидратации**: JS на клиенте вообще не участвует в
построении интерфейса.
